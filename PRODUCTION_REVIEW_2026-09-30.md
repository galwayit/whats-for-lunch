**What We Have for Lunch — production and App Store review, 30 September 2026**

**Decision: hold the production release.** The native app has substantial implementation and automated coverage, but the current checkout cannot produce a configured production archive. There are also access-control, purchase, privacy, and guest-invitation defects to close before accepting paying customers.

Scope: the `native-migration` working tree based on `22c32c1`, including its existing modified and untracked files. Android UI and the archived Flutter app were not comprehensively audited. No application code, account configuration, deployment, or store submission was changed by this review.

**Findings to fix before release**

1. **[P1] Bind backend entitlement checks to an authenticated identity.** [auth.ts:68](/Users/rayding/galway/what_we_have_for_lunch/backend/supabase/functions/_shared/auth.ts:68) returns `x-app-user-id` before considering the verified user. AI requests and group creation then use that value for paid access and usage accounting. A local reproduction with authenticated user A and a different header resolves the other identity. Anonymous callers can also rotate arbitrary IDs to obtain fresh quotas. Knowing another paid user's identifier is sufficient to select that entitlement; an identifier is not an authentication secret. Derive signed-in identity from the verified JWT. Preserve guest access using a server-issued, verifiable anonymous principal, with an explicit purchase-to-principal binding. Add rejection tests for mismatched IDs and expired anonymous credentials.

2. **[P1] Enforce AI quotas atomically and bound public API spending.** [ai-recommend/index.ts:94](/Users/rayding/galway/what_we_have_for_lunch/backend/supabase/functions/ai-recommend/index.ts:94) reads usage, checks it, and increments in separate operations. Concurrent calls can all pass the same free allowance; the SQL increment has no upper-bound condition. The caller also chooses the time zone used to select the quota day. Replace this with one atomic reservation operation, a stable quota-day policy, and idempotent refund handling. Public Places/photo and invitation endpoints have no application rate limiter in the reviewed code. Add per-principal/IP limits, body/prompt-size limits, upstream deadlines, provider quotas, and cost alerts. Deployed edge-level controls were not verified.

3. **[P1] Make third-party AI consent cover group recommendations.** [GroupProposalsViewModel.swift:29](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/Features/Group/GroupProposalsViewModel.swift:29) calls the shared proposal service on load. That service sends the host's preferences, and the backend sends them to Gemini. The consent guard exists only in `AIRecommendationsViewModel`. A host can reach the group flow without consenting on that screen. Move consent enforcement into a common boundary used by both flows, provide a withdrawal control, and test both refusal paths. Publish the corrected privacy policy and align App Store privacy answers with the actual data flow. Apple explicitly requires permission before personal data is shared with third-party AI. [Apple review guidelines, 5.1.2(i)](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing)

4. **[P1] Correct the subscription promises and trial display.** [Copy.swift:272](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/Copy/Copy.swift:272) promises a seven-day trial, backup/sync, and PDF export. The implemented export writes [lunch-export.json](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/Features/Profile/ProfileViewModel.swift:61), and the reviewed profile/meal repositories store data in local SQLite without a cross-device sync service. [PaywallView.swift:38](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/DesignSystem/Components/PaywallView.swift:38) always prints the trial sentence; the package mapping checks that a product has an introductory offer, rather than the current customer's eligibility. Remove unfinished benefits for v1, derive trial duration and eligibility from the store, and show immediate-charge wording for ordinary subscriptions. Verify new, returning, and ineligible subscribers. Accurate functionality and subscription disclosures are review requirements. [Apple review guidelines](https://developer.apple.com/app-store/review/guidelines/)

5. **[P1] Reconcile RevenueCat status instead of trusting incomplete event mappings.** [revenuecat.ts:82](/Users/rayding/galway/what_we_have_for_lunch/backend/supabase/functions/_shared/revenuecat.ts:82) treats a missing transfer source as an entitlement with no expiry; the local reproduction grants permanent Pro to the destination. It also treats any nonempty entitlement list as Pro, while the client specifically expects `pro`. The handler has no event-ID ledger or ordering protection, so a delayed older event can overwrite newer state. Reconcile the exact `pro` entitlement against RevenueCat's current subscriber state, fail closed when it cannot be established, and make event processing idempotent. Define production/sandbox routing explicitly. RevenueCat recommends subscriber-state reconciliation and duplicate-event handling. [RevenueCat webhooks](https://www.revenuecat.com/docs/integrations/webhooks)

6. **[P1] Preserve anonymous invitation identity in the native client.** The [native invitation screen](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/Features/Invitation/InvitationView.swift:61) supports signed-out guests. The backend returns a guest token, but [KtorBackendClient.kt:95](/Users/rayding/galway/what_we_have_for_lunch/shared/src/commonMain/kotlin/au/iapp/lunch/core/network/KtorBackendClient.kt:95) returns only the invitation and never persists or sends `x-guest-token`. Reopening the link loses `myStatus`, and a second response can create another RSVP. Persist the token securely per invitation and send it for reads and writes. Test accept → relaunch → reopen → change response against the actual HTTP contract, checking that one RSVP remains.

7. **[P1] Complete Sign in with Apple account deletion.** [account-delete/index.ts:12](/Users/rayding/galway/what_we_have_for_lunch/backend/supabase/functions/account-delete/index.ts:12) deletes Supabase data and its auth user, but no Apple token revocation path exists. [SignInTokens.swift:90](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/Features/Auth/SignInTokens.swift:90) forwards an identity token and nonce without the authorization-code exchange needed for the revocation flow. Implement the server-side Apple revocation flow and retry-safe deletion, and test deletion followed by a fresh Apple sign-in. The existing disclosure intentionally retains local meals; make that choice clear and offer local-data removal separately. Apple calls for revoking Sign in with Apple tokens when an account is deleted. [Apple account-deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

8. **[P1] Carry Google Places attribution through to the UI.** [places.ts:140](/Users/rayding/galway/what_we_have_for_lunch/backend/supabase/functions/_shared/places.ts:140) reduces photos to resource names, dropping author attribution; review mapping also drops the author's profile link. Restaurant cards/details display the content without the required Google branding and photo-author attribution. Add attribution fields across backend DTOs, Kotlin, and Swift UI. Review the full-payload database caches, stale local fallback, and photo-name persistence against the applicable Google agreement; a 24-hour TTL alone does not establish permission to cache all content. Google's published policies require attribution and restrict storage, with specific exceptions such as place IDs. [Google Places policies](https://developers.google.com/maps/documentation/places/web-service/policies) and [photo requirements](https://developers.google.com/maps/documentation/places/web-service/place-photos)

9. **[P1 before enabling push] Rebind device tokens on account changes.** [LunchAppDelegate.swift:55](/Users/rayding/galway/what_we_have_for_lunch/iosApp/LunchApp/App/LunchAppDelegate.swift:55) submits a token and clears its pending copy. Sign-in/sign-out in [AuthRepositoryImpl.kt:58](/Users/rayding/galway/what_we_have_for_lunch/shared/src/commonMain/kotlin/au/iapp/lunch/core/service/AuthRepositoryImpl.kt:58) neither re-registers nor removes that binding. A token first registered anonymously can miss user-addressed group notifications; a signed-out device can remain associated with the previous account. Add registration on identity change, authenticated unregistration on sign-out, retry on reconnect, and notification-tap routing. Validate APNs → FCM → backend → physical device delivery after providing the missing Firebase configuration.

10. **[P2] Expose group-load failures and refresh shared state.** [GroupRepositoryImpl.kt:42](/Users/rayding/galway/what_we_have_for_lunch/shared/src/commonMain/kotlin/au/iapp/lunch/core/service/GroupRepositoryImpl.kt:42) fetches once, while both group/RSVP flows swallow errors and complete without a result. The screens can retain an empty/loading view without a useful error and do not continuously receive other guests' responses. Return an explicit load/error state and use authenticated realtime or deliberate foreground refresh. Local reminders are acceptable for v1, but restore the toggle from scheduled notifications and avoid promising cross-device reminders.

**Recommended release sequence**

1. Keep SwiftUI + Kotlin Multiplatform + Supabase. Another rewrite would add migration risk without resolving the observed defects. Use Apple-only sign-in for v1; Google sign-in can wait. Remove backup/sync and PDF claims until those features exist. Keep optional AI/group hosting only if their acceptance tests pass.
2. Fix identity binding, atomic quotas, entitlement reconciliation, guest-token persistence, consent, deletion and attribution. Add targeted regression and database/HTTP integration tests around these boundaries.
3. Verify private service configuration, reconcile deployments and complete the real sandbox purchase and physical-device tests. Test group-name/guest-name abuse handling, guest removal/reporting and invitation invalidation because shared user content can raise App Review concerns. Also test VoiceOver, larger text and the supported iOS versions.
4. Choose the intended App Store listing explicitly. Native iOS uses `au.iapp.lunch`, while archived Flutter uses `au.iapp.guesswhat.whatWeHaveForLunch`. Those identities cannot deliver an in-place update to each other. Even if continuity is restored, Flutter stored SQLite under Documents and native iOS now uses Application Support/Lunch; add a file-location migration and an installed-app upgrade test. Schema-fixture tests cover only part of that migration.
5. Produce a signed, configured Release archive; validate its entitlements, SDK/privacy report and embedded configuration. Upload to TestFlight, run acceptance on that exact build, finish the required screenshot/metadata set, and submit the selected build and subscriptions to App Review. Publication follows Apple's approval and the chosen release setting.

For model maintenance, the backend currently hardcodes `gemini-2.5-flash-lite` and `gemini-2.5-flash`. Google's current documentation limits 2.5 access to projects that previously used it and recommends newer models for new projects; it does not list these two models as shut down. Make model IDs configurable, verify access with the production project, and compare supported models on recommendation quality, JSON validity, latency and cost before selecting a replacement. Preserve the tested Kotlin/SKIE/RevenueCat version chain until a deliberate compatibility upgrade is validated. [Gemini lifecycle documentation](https://ai.google.dev/gemini-api/docs/deprecations)

Prior handoff notes about those accounts may be stale. Read-only authorization is needed to close those account checks; it will not resolve the confirmed code defects or missing release configuration by itself.
